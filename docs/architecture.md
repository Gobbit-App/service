# Architecture — Gobbit (Community Pocketbook) Phase 5

## Overview

Gobbit (repository: community-pocketbook) is a monorepo (pnpm) organizing shared logic, persistence, API, and testing into isolated, typed packages.

### Workspace structure

- **`@pb/shared`** (packages/shared): Enums, limits, validation schemas (Zod), and utility functions. Single source of truth for domain constraints. Exports normalized to one entry point.
- **`@pb/db`** (packages/db): Drizzle ORM schema, migrations (drizzle-kit generated + hand-written custom), seeding logic, and database client. Exposes migrations, schema types, test fixtures.
- **`@pb/api`** (apps/api): Hono REST API with OpenAPI documentation. Layered: routes (parse input) → services (rules) → repositories (SQL). Error handling via RFC 9457 Problem+JSON. Magic-link sign-in with server-side sessions, per-deck roles and category visibility (Phase 2).
- **`e2e`** (e2e/): Playwright test suite with smoke tests tagged `@smoke`.
- **`@pb/api-client`** (packages/api-client): OpenAPI document (`openapi.json`) and generated types (`src/schema.d.ts`) from the API routes; `createApiClient()` (openapi-fetch, base `/api`) and `$api` (openapi-react-query). Regenerated by `pnpm api:openapi`; CI fails on drift (D53).
- **`@pb/web`** (apps/web): Reader PWA (Phase 3). React 19 + Vite, TanStack Router (file routes) and Query, `vite-plugin-pwa`. Built to static files and served by its own Caddy image, which also routes `/api` and `/s` to the API (D51).

All packages are private, ES modules, strict TypeScript. Runtime via `tsx` (no build step). TypeScript source is published as-is, with tsconfig.base.json enforcing `target ES2022, module ESNext, strict` (`noUncheckedIndexedAccess` deliberately off — see ADR-022).

### Key design patterns

- **Soft deletes**: All user-facing tables have `deleted_at` timestamp. Queries always filter `WHERE deleted_at IS NULL` unless explicitly archiving.
- **Denormalization**: `item_categories` includes `deck_id` to enable composite FK constraints without a separate join.
- **Unique constraints on slugs**: Partial unique indexes on slug + deck where `deleted_at IS NULL` prevent collisions among active records.
- **Timestamps with millisecond precision**: All `timestamptz` columns use `precision: 3` (JavaScript Date compatibility required for keyset cursors).
- **Invariant triggers**: Database enforces cross-table rules (default category protection, auto-creation, timestamps).

## Invariants

| Invariant | Description | Enforced by |
|-----------|-------------|------------|
| **Published item → ≥1 category** (master plan P1.2) | An item with status='published' must have at least one category. | Service only: `items.create()` (D6 assigns `general` when none given) and `items.update()` rejects a result that would be published with no categories. The master plan's "trigger later" is not scheduled yet. |
| **D5: item_categories dual FK** | Each item_category row references both item and category via composite FK, ensuring consistency. | Drizzle schema composite FK with ON DELETE CASCADE. |
| **D6: Empty categoryIds → default** | If item created with no categoryIds, automatically assign default category of deck. | Service `items.create()` after fetching default. |
| **D7: Default category auto-create + protect** | Every deck gets a 'general' default category on insert. Cannot be deleted or have is_default=false. | DB trigger `decks_create_default_category` (INSERT) + `categories_protect_default` (DELETE/UPDATE); unique index `categories_one_default_uq` ensures ≤1 default per deck. |
| **D3: Slugs** | `decks.slug` unique among live decks; `categories.slug` unique per deck. | Partial unique indexes `decks_slug_active_uq`, `categories_deck_slug_active_uq` (`WHERE deleted_at IS NULL`); 23505 → 409. |
| **D8: Body budget** | `body` ≤ `CARD_BODY_MAX` (600) Unicode code points. | zod `itemBodySchema` in @pb/shared; DB check constraint on `char_length(body)` (`0003_card_limits`). |
| **Personal deck (Phase 3B, supersedes D25's no-auto-deck)** | Each account has exactly one personal deck (`is_default`), ensured on every sign-in. It cannot be deleted, shared, re-slugged or made public; its address is `me`. | Partial unique index `decks_default_per_account_uq`; CHECKs `decks_default_is_personal`, `decks_slug_not_reserved`; trigger `decks_protect_default` (P0001 `default_deck_protected`). Service rules answer 409 `/problems/personal-deck`. |
| **Soft delete** (master plan P1.1, ADR-005) | Deleting sets `deleted_at` on accounts, users, decks, categories, items and memberships; queries exclude soft-deleted rows. Join tables (`item_categories`, `favorites`) are hard-deleted by design. | All repository `.find*()`, `.list()` include `WHERE isNull(t.deletedAt)`. Service `items.softDelete()`. |
| **Auto `updated_at`** (master plan P1.1) | Every update to accounts, users, decks, categories, items and memberships sets `updated_at = now()`. | DB trigger `<table>_set_updated_at` BEFORE UPDATE on each table. |
| **D9/D10: Payload budget and shape** | Each item type (text, link, image, table, calc) validates payload against a strict Zod schema. Payload ≤ 8192 UTF-8 bytes; DB enforces ≤ 9216 with a check constraint. | `payloadSchemaFor(type)` and the byte budget in @pb/shared (zod is authoritative); service calls `parse()` on PATCH; DB check constraint `items_payload_size_chk`. |
| **D12: Item type immutable** | Cannot PATCH an item's type. | Service `items.update()` rejects `'type' in patch` with 400. |
| **D13: Status default published** | Item created without a status defaults to 'published' and `verified_at = now()`. | Service `items.create()` sets both. `verified_at` is the publish time, not a review; the Reader shows "Added/Edited … ago" from `created_at`/`updated_at` instead (`lib/card-age.ts`). |
| **D14: Pagination keyset cursor** | Cursor encodes (createdAt, id) tuple, limiting result sets. Limit default 20, max 50; >50 rejects. | `limitSchema` in @pb/shared; `itemListQuerySchema`; service `items.list()` decodes, queries with SQL keyset filter. |
| **D15: Favorite idempotence** | Adding/removing favorite twice is safe (no error). | Repository `favorites.add()` uses `onConflictDoNothing`; `favorites.remove()` does not error if missing. |
| **D16: Session auth gate** (Phase 2, replaces dev auth) | Routes that need a caller require a valid session (bearer or cookie); anonymous requests to them get 401. `/health`, `/openapi.json`, `/auth/magic-link` and `/auth/callback` are open. | Middleware `sessionAuth()` resolves the caller but never demands one; each protected route calls `getUser()` (401). A stale or invalid cookie is 401 + cleared, except on `LENIENT_PATHS` (the four open paths), where it is ignored so a signed-out browser can still sign in. |
| **D17: Access control** (Phase 2: D33–D35) | No role on a deck → 404; a role without the permission → 403 `/problems/forbidden`. | `authorize()` in `access/authorize.ts` (`resolveRole` + `can()`), called by every deck-scoped service method. |
| **D36: One membership per user–deck** | Partial unique `(deck_id, user_id) WHERE deleted_at IS NULL`; owner-account users can't be members of their own decks. | Unique index + `BEFORE INSERT OR UPDATE OF deck_id, user_id` trigger raising `owner_account_membership` (`0005_auth_triggers`), mapped to 400. |
| **D18: Problem schema** | All errors returned as RFC 9457 problem+json with type URL, status, title, detail, and optional field errors. | `Problem`, `ProblemFieldError` schemas in @pb/shared; error handlers in middleware convert Zod, pg, and app errors. |
| **D19: Migration rollback** | `db:rollback` reverses the latest applied migration by running its `.down.sql` and deleting the journal entry. | `rollbackLatest()` in `src/migrations.ts` executes down file in transaction, maps tag from __drizzle_migrations. |
| **D21: E2E smoke tests** | Tagged tests `@smoke` each create and delete their own `smoke-<id>` deck (D50), all read /health before starting. | Playwright config `testDir: ./tests`, global-setup waits for health + latest migration tag match. |

## Layering & Architecture

### Request flow

```
Route (HTTP handler, parses input via Zod)
  ↓
Service (business logic, access control, cascades)
  ↓
Repository (Drizzle SQL, returns Row types)
  ↓
Mapper (Row → DTO, Date → ISO string)
  ↓
HTTP Response (JSON, status code, problem+json on error)
```

### Single source of truth: @pb/shared schemas

All DTOs, constraints, and enums live in @pb/shared:
- **Limits** (CARD_TITLE_MAX=120, CARD_BODY_MAX=600, PAGE_LIMIT_MAX=50, PAYLOAD_MAX_BYTES=8192, etc.)
- **Enums** (deckKinds, categoryVisibilities, itemTypes, itemStatuses, sourceKinds)
- **Validation** (Zod schemas for create/patch inputs, payloads, pagination, problems)
- **Utilities** (UTF-8 byte counting, cursor encoding/decoding, calc expression validation)

Services and repositories import these, ensuring consistency across API, tests, and migrations.

### Route registration

Routes use `@hono/zod-openapi`:
- Input: path params (z.object), query (z.object), JSON body (z.object)
- Output: 200/201 with content schema; 4xx/5xx with `problemSchema`
- Metadata: method, path, security (`AUTH_SECURITY` = `SessionCookie` or `BearerToken`), description
- Handler: receives validated input, calls service, returns DTO or 404/409/422

Example pattern:
```ts
const route = createRoute({
  method: 'post',
  path: '/decks/{id}/items',
  request: { 
    params: z.object({ id: z.string().min(1) }),
    body: { content: { 'application/json': { schema: itemCreateSchema } }, required: true }
  },
  responses: {
    201: { content: { 'application/json': { schema: itemSchema } } },
    400: { content: { 'application/problem+json': { schema: problemSchema } } }
  },
  security: AUTH_SECURITY
});

app.openapi(route, async (c) => {
  const user = getUser(c);
  const { id } = c.req.valid('param');
  const input = c.req.valid('json');
  const item = await services.items.create(user, id, input);
  return c.json(item, 201);
});
```

### Service layer

Services encapsulate business rules:
- **Access control**: `authorize(user, deck, permission, memberships)` resolves the role and asserts the permission
- **Validation**: call Zod `parse()` on structured inputs (e.g., payload by type)
- **Cascades**: when creating a deck, fetch the default category; when updating an item, maybe recompute isFavorite
- **Soft delete**: use repository methods; service owns the semantics (e.g., `archive()` is idempotent)

### Repository layer

Repositories abstract SQL:
- **Queries exclude soft-deleted**: `where(isNull(t.deletedAt))`
- **Return row types**: `accountId: string | null` if nullable in DB
- **Transactions**: item creation inserts item + item_category rows atomically
- **No business logic**: repositories are thin data accessors

### Mappers

Convert database rows to API DTOs:
- Dates: `Date → ISO string` (via `.toISOString()`)
- Nullable dates: remain `null`
- Extra fields: `categoryIds`, `isFavorite` fetched separately, attached in service
- Type consistency: TS strict mode ensures no `undefined`

## Error Format & Status Codes

### RFC 9457 Problem+JSON

All errors (except 5xx) follow the Problem schema:

```json
{
  "type": "/problems/validation",
  "title": "Validation failed",
  "status": 400,
  "detail": "...",
  "errors": [
    { "path": "categoryIds", "message": "Unknown categories" }
  ]
}
```

### Error mapping table

| Scenario | Status | type | title | Detail |
|----------|--------|------|-------|--------|
| Zod parse fails | 400 | /problems/validation | Validation failed | From ZodError |
| Payload exceeds 8192 bytes | 400 | /problems/validation | Validation failed | "Payload exceeds 8192 bytes (UTF-8)" |
| Cursor invalid base64 | 400 | /problems/invalid-cursor | Invalid cursor | "Invalid cursor" |
| Invalid calc expression | 400 | /problems/validation | Validation failed | "Invalid expression: ..." |
| Missing Authorization | 401 | /problems/unauthorized | Unauthorized | "Authentication required" |
| Deck not found | 404 | /problems/not-found | Not Found | "Deck not found" |
| Item not found | 404 | /problems/not-found | Not Found | "Item not found" |
| Route not found | 404 | /problems/not-found | Not Found | "Route not found" |
| Slug already exists (pg 23505) | 409 | /problems/conflict | Conflict | "Resource already exists" |
| Default category protected (pg P0001) | 409 | /problems/default-category-protected | Default category is protected | From constraint |
| Foreign key missing (pg 23503) | 422 | /problems/invalid-reference | Invalid reference | "Invalid reference" |
| Check constraint (pg 23514) | 422 | /problems/constraint-violation | Constraint violation | "Constraint violation" |
| Immutable field (type) in PATCH | 400 | /problems/bad-request | Bad Request | "Item type is immutable" |
| Published item no categories | 422 | /problems/item-needs-category | (custom) | "A published item needs at least one category" |
| PATCH archived → published (Phase 6, D131) | 409 | /problems/use-restore | Conflict | Points to `POST /items/{id}/restore` |
| Archive/restore a proposal (D131) | 409 | /problems/invalid-transition | Conflict | "A proposal can't be archived/restored; …" |
| Undelete after 30 days (D132) | 410 | /problems/undo-expired | Gone | "Deleted cards can be brought back for 30 days" |
| `?status=deleted` without `item.delete` (D132) | 403 | /problems/forbidden | Forbidden | Names the permission |
| 5xx (unhandled) | 500 | /problems/internal | Internal Server Error | (omit internals from response) |

### Error handler middleware

- Catches exceptions during request handling
- `instanceof HttpError`: convert to Problem
- `instanceof ZodError`: convert via `problemFromZodError()`
- `instanceof InvalidCursorError`: 400 /problems/invalid-cursor
- `mapPgError(err)` detects pg codes (23505, 23514, 23503, P0001); non-null → respond with mapped Problem
- All other errors: log with requestId, respond 500 /problems/internal (no stack trace to client)
- Request log (`middleware/request-log.ts`): one stdout line per request, `[api] METHOD /path STATUS 12ms <requestId>`. It is registered first, so CSRF rejections are logged too. The query string is never logged (search text stays out of logs), `/health` is skipped, and it is off when `NODE_ENV=test`.

## Pagination

### Keyset cursor pattern

Instead of offset, use the last row's sort key to fetch the next batch:

```ts
// First request: no cursor
GET /decks/{id}/items?limit=20

// Response
{
  "data": [...],
  "nextCursor": "eyJjIjoiMjAyNC0wMS0xNVQxMDozMDowMCswMDowMDAiLCJpIjoiYWJjZC4uLiJ9"
}

// Next request
GET /decks/{id}/items?cursor=eyJjIjoiMjAyNC0wMS0xNVQxMDozMDowMCswMDowMDAiLCJpIjoiYWJjZC4uLiJ9&limit=20
```

### Cursor encoding/decoding

- **Encode**: `Buffer.from(JSON.stringify({ c: isoString, i: uuid })).toString('base64url')`
- **Decode**: base64url → JSON → `{ createdAt: string, id: string }` OR throw InvalidCursorError
- **Format**: `(createdAt, id) < cursor.values (both DESC)`

### Limits

- **Default**: 20 items
- **Max**: 50 items
- **>50 rejected**: request validation fails (400)
- **≤0 rejected**: request validation fails (400)

### Pagination schema

```ts
limitSchema = z.coerce.number().int().min(1).max(PAGE_LIMIT_MAX).default(PAGE_LIMIT_DEFAULT)
pageSchema<T>(item: T) = z.object({ 
  data: z.array(item), 
  nextCursor: z.string().nullable() 
})
```

## Authentication

### Magic links (D22–D26)

1. `POST /auth/magic-link { email }` always answers `200 { ok: true }` (no account enumeration; a malformed email is `400`). Rate limits run first (see below). The link token is `base64url(randomBytes(32))`; only `sha256(token)` is stored in `magic_links.token_hash`.
2. The mail (`Mailer`: `ResendMailer` / `ConsoleMailer` / `MemoryMailer`, chosen by `MAIL_PROVIDER`) carries `${API_URL}/auth/callback?token=…`. Sign-in links live `MAGIC_LINK_TTL_MINUTES` (15), invite links `INVITE_TTL_DAYS` (7).
3. `GET /auth/callback?token=` consumes the link with one atomic `UPDATE … WHERE used_at IS NULL AND expires_at > now() RETURNING *` (zero rows → invalid/used/expired, reason derived afterwards). The user is found or created in exactly one place, `users.service.findOrCreateByEmail()` (D25). For invites it sets `accepted_at`. In the same transaction, `usersService.ensurePersonalDeck()` makes sure the user has a personal deck (Phase 3B) before the cookie session opens; a failure there rolls the whole callback back and redirects to `/auth/error?reason=onboarding`. It answers `303` to `${APP_URL}${next}` (or `${API_URL}/me` without `APP_URL`); `next` must be a relative path (`^/[^/\\]`). A bad link → `303 ${APP_URL}/auth/error?reason=…` or `401 /problems/magic-link-invalid`.

### Sessions (D27–D31)

- `sessions` rows are opaque random tokens stored as hashes, `kind` `cookie | bearer`, sliding lifetime `SESSION_TTL_DAYS` (90): `last_seen_at`/`expires_at` are bumped in one `UPDATE` at most once an hour.
- Cookie `gobbit_session`: `HttpOnly`, `SameSite=Lax`, `Path=/`, `Secure` per `COOKIE_SECURE`, `Domain` per `COOKIE_DOMAIN` (host-only when unset).
- **Precedence**: `Authorization: Bearer` first; the cookie only when no bearer header exists. A bad bearer is `401 /problems/session-invalid` even with a valid cookie.
- `POST /auth/token-exchange` (cookie-authenticated only) mints a separate `bearer` session and returns `{ token, expiresAt }` once.
- `POST /auth/logout` revokes the current session (clears the cookie); `POST /auth/logout-all` revokes all of the user's sessions.
- Lookup is by hash, then `timingSafeEqual` on the stored hash. All expiry logic reads the injected clock `now()` (D42).

### CORS and CSRF (D32)

`hono/cors` with `CORS_ORIGINS` and `credentials: true`. `middleware/csrf.ts` wraps `hono/csrf` over `CORS_ORIGINS` plus the API's own origin, for cookie-authenticated unsafe requests; requests with an `Authorization` header skip it. Rejections are `403` problem+json.

### Deployment layout (D46)

Images come from GHCR (ADR-033); the database is a shared Postgres outside the Compose project (ADR-039); backups and restore are in `infra/README.md`. One origin `https://gobbit.niranhome.win`: Traefik routes `PathPrefix(/api)` to the API with a strip-prefix middleware (labels in `infra/docker-compose.yml`), so `API_URL=https://gobbit.niranhome.win/api`, `COOKIE_DOMAIN` unset, `CORS_ORIGINS=https://gobbit.niranhome.win`, `CLIENT_IP_HEADER=cf-connecting-ip`.

## Personal deck and first card (Phase 3B)

Supersedes D25's "no deck is auto-created": every account gets exactly one personal deck, ensured on every sign-in (new users, invitees, and accounts that predate this phase; no backfill migration).

- **Marker**: `decks.is_default` (TS `isDefault`) marks the personal deck. Its `kind` is `personal`, but other decks can also be `personal`, so code finds it only by the flag: `decks.repo#findDefaultForAccount(accountId)`.
- **DB invariants** (migration `0007_default_deck`, hand-written part appended to the generated SQL; down file `migrations/down/0007_default_deck.down.sql`): partial unique index `decks_default_per_account_uq` on `(owner_account_id) WHERE is_default AND deleted_at IS NULL`; CHECK `decks_default_is_personal` (`NOT is_default OR kind = 'personal'`); CHECK `decks_slug_not_reserved` (`slug <> 'me'`); trigger `decks_protect_default` (BEFORE DELETE OR UPDATE OF deleted_at, is_default) raising `default_deck_protected` (P0001) unless `pg_trigger_depth() > 1`, so an account delete can cascade.
- **Ensure**: `usersService.ensurePersonalDeck(user)` sits next to `findOrCreateByEmail()`. It inserts with `ON CONFLICT DO NOTHING` and reads the row back (`ensureDefault`), so it is idempotent. `GET /auth/callback` runs consume link, find or create user, ensure deck, open session in one transaction (`buildCallbackRepos` in `services/index.ts`). An ensure failure is logged (`[auth] onboarding failed`) and surfaces as `MagicLinkFailure('onboarding')`.
- **Address**: the stored slug is `personal-<accountId>` and is never shown. `resolveDeck` maps `me` to the caller's default deck (404 when there is none), and `toDeckDto` returns `slug: 'me'` when `isDefault`. `me` is `RESERVED_DECK_SLUG` in `@pb/shared`, which no other deck can take. The default name is `PERSONAL_DECK_NAME` ("My deck") and can be renamed.
- **409 rules** (`/problems/personal-deck`): deleting the deck, patching `slug` or `isPublic` on it, and inviting a member to it. Renaming is allowed.
- **Landing (web)**: `pickLanding` in `lib/last-deck.ts` opens the last deck if it is still listed, else `me`, else the only deck, else the home list. The home empty state reads "No pocketbooks yet".
- **Card editor (web)**: `/d/$slug/new` (`routes/d.$slug.new.tsx`) renders `CardEditor` inside the deck layout. It creates text and link cards only, with the category defaulting to the deck's default one. `useCreateItem` posts to `POST /decks/{id}/items` and invalidates every item list. API field errors show in `role="alert"` (`problemMessages`). The "Add card" link (`AddCardLink`) appears only for roles with `item.create`.

## Authorization (D33–D35)

- `resolveRole(user, deck, membership)`: users of the deck's `owner_account_id` are implicitly `owner`; otherwise the **accepted** membership's role; pending or none → no role.
- `can(role, permission)` (`@pb/shared` authz) is a pure table over the `Permission` union; the matrix is unit-tested exhaustively.
- `authorize()` combines both: no role → `404` (ADR-004); role lacking the permission → `403 /problems/forbidden` with `permission` and `role` extension members.
- `GET /decks` and `GET /me` return owned ∪ accepted-member decks, each with the caller's `role`.
- Memberships: `GET /decks/:id/members` (implicit owner first, pending included), `POST /decks/:id/invites { email, role }` (creates the user if needed, pending membership + invite link; `201`, resend `200`, accepted member `409`, self `400`), `DELETE /decks/:id/members/:userId`.
- A resend to a pending member replaces the invite: the membership takes the new `role`, inviter and `invited_at`, and every unused invite link of that membership is expired (it reports `reason=expired`), so only the newest link works.
- `owner` memberships (co-admins) get every owner permission except `deck.delete`: `DELETE /decks/:id` additionally requires the caller to belong to the deck's owner account (`403 /problems/forbidden`, `permission: deck.delete`, `role: owner`). This is the one rule outside the `can()` matrix (D34 had deferred resource-level rules).

## Visibility (D38)

`visibleCategoriesWhere(role)` (`access/visibility.ts`) is the single predicate: owner/maintainer → all; editor/reader → `shared` + `public`; no role → `public` (Phase 8). It is applied in:

1. category listing,
2. item listing (`EXISTS` over `item_categories ⋈ categories`, so pagination stays consistent),
3. item get (no visible category → `404`),
4. the `?category=` slug filter (invisible → `404`),
5. `categoryIds` validation on create/patch (invisible → `400`),
6. the item DTO (`categoryIds` lists only visible categories).

## Rate limits (D39–D40)

Postgres table `rate_limit_counters`, fixed one-hour windows, `INSERT … ON CONFLICT DO UPDATE SET count = count + 1 RETURNING count`. Keys and limits (from `@pb/shared`): `magic-link:email:<sha256>` 5, `magic-link:ip:<ip>` 20, `callback:ip:<ip>` 30; Phase 6 adds `media-sign:user:<id>` 60 and `link-preview:user:<id>` 30 (008). The email counter is checked before any user lookup, so a `429 /problems/rate-limited` (with `Retry-After`) reveals nothing. Rows older than two windows are purged on ~1% of increments. The client IP is the socket address unless `CLIENT_IP_HEADER` names a trusted header; `X-Forwarded-For` is never trusted implicitly.

## Seeding and test data (D49)

### Owner-only seed

`pnpm db:seed` (`packages/db/scripts/seed.ts` → `seed/run-seed.ts`) upserts exactly **one account and one user** — the owner — and nothing else. No decks, categories or cards are seeded; a fresh deployment starts empty.

- `SEED_OWNER_EMAIL` is required (the script exits non-zero without it); `SEED_OWNER_NAME` defaults to the email local part. Parsing lives in `seed/owner.ts` (`parseOwnerSeedEnv`).
- Ids are uuid v5 under `SEED_NAMESPACE` (`seedId('owner')` for the account, `seedId('owner/user')` for the user), so re-running upserts in place.
- Idempotent: `ON CONFLICT … DO UPDATE … WHERE … IS DISTINCT FROM`, so a second run with the same values leaves `updated_at` untouched; a changed name or email updates the row in place.
- Local development only: the script refuses `NODE_ENV=production` outright (Oct 1). A deployed instance is never seeded; the owner's first magic-link sign-in creates the user (D25).
- `SMOKE_SESSION_TOKEN` (D43, ≥32 chars) upserts one 365-day `bearer` session for the owner (`user_agent = 'smoke'`); re-running with a new token rotates it. No other users are seeded.

### Test factories (`@pb/db/test`)

Integration tests build their own data; nothing depends on seeded rows.

- `factories.ts`: `createAccountUser`, `createDeck` (the trigger adds `general`), `defaultCategory`, `createCategory`, `createItem` (runs the card through `itemCreateSchema`, links categories, defaults to `general`), `addFavorite`. Ids come from `fixtureId(key)` — uuid v5 under a separate `FIXTURE_NAMESPACE`.
- `fixtures/sample-cards.ts`: the 25 Phase 1 cards (`SampleCard`: `ItemCreate` + category slugs + status/lang/favorite), and `SAMPLE_CATEGORIES`. Its unit test pins the shape the suites rely on: 23 published + 2 archived, 12 food (all published), 2 table, 1 calc, 1 favorite, he/el/en.
- `sample-world.ts`: `createSampleWorld(db)` reproduces the Phase 1 layout — owner (`owner@example.test`) with decks `personal` (empty), `family` (six categories + the 25 cards), `scratch` (empty), and a second user (`other@example.test`) with `other-personal`. `apps/api/test/helpers.ts#setupApiTest()` builds it once per suite and exposes it as `world`.

## Search (Phase 4)

### Data (migration `0008_search`)

- Extensions `vector` (pgvector) and `pg_trgm`. Compose and Testcontainers use `pgvector/pgvector:pg17`.
- `items.search_text` is a generated, stored column built by `item_search_text(type, title, body, payload)`. It holds the title, body and type-specific payload text (URLs, table cells, calc labels, image alt), passed through `search_normalize()`. That function lowercases, folds Greek tonos, strips Hebrew points and combining marks, maps the maqaf to a space, and removes separators between digits (`054-771 2345` → `0547712345`). A GIN trigram index sits on it.
- `items.embedding vector(1536)` (HNSW, cosine, `m=16, ef_construction=64`), plus `embedding_model`, `embedded_hash` and `embedded_at`. An item is stale when `item_embedding_hash(search_text)` or the model differs from what is stored.
- `search_queries` gets one row per search or ask: deck, user, mode, normalized q, result count, top `why` and latency. A weekly job prunes rows older than 180 days.
- `llm_calls` gets one row per provider call: purpose (`embed_item`, `embed_query`, `ask`), provider, model, tokens, estimated `cost_usd`, latency and status. No prompt or answer text is stored.
- The `items_set_updated_at` trigger fires only `BEFORE UPDATE OF` user-facing columns, so writing the embedding columns leaves `updated_at` alone.

### Query path (`GET /decks/{id}/search?q=&limit=`)

```
route (Zod: q 1..200, limit ≤ 20) → searchService.search
  authorize(viewer) → normalize(q) (SQL search_normalize) → query vector (LRU cache, hourly budget; null without an embedding key)
  → searchRepo.hybrid: text arm  (word_similarity ≥ 0.4 on search_text, plus a substring arm; skipped below 3 chars)
                       vector arm (cosine distance ≤ 0.55, same model, hnsw.ef_search 100)
                       each ≤ 50 rows, published and not deleted, limited to the categories the role can see
  → fuseRrf (k = 60, substring hits get +1/60) → DTOs with why ∈ {text, semantic, both} → log search_queries
```

- The response is `{ data: [{ item, why, score }], semantic }`. `semantic` is false when the vector arm didn't run (no key, over budget, provider error).
- The web highlights matches client-side with `highlight()` from `@pb/shared/search`, which folds text the same way the SQL does.
- Without an embedding key (`OPENROUTER_API_KEY` or `OPENAI_API_KEY`, ADR-044), search runs text-only and nothing is enqueued.

### Ask (`POST /decks/{id}/ask`)

- Without an Ask key (`OPENROUTER_API_KEY` or `ANTHROPIC_API_KEY`) Ask answers 503. `/config` then reports `search.ask: false`, and the PWA hides the mode toggle.
- Next comes the per-user rate limit (30/hour, the Phase 2 Postgres limiter), checked before any retrieval.
- Retrieval reuses the search path. The top 8 hits go into a prompt (`ai/ask-prompt.ts`) that asks for a short answer in the question's script, citing card ids. `ai/ask-citations.ts` keeps only citations among the retrieved cards.
- The model is `ASK_MODEL` (default Claude Haiku 5.5: `anthropic/claude-haiku-5.5` on OpenRouter, `claude-haiku-5-5` on Anthropic) with a 20 s deadline. A timeout answers 504; a provider failure answers 503.
- No hits, an ungrounded answer or no valid citations → a localized "not found" answer with `grounded: false` and no citations.

### Embeddings worker (`apps/api/src/worker.ts`)

- The worker is a separate process from the same API image (`pnpm --filter @pb/api worker`; the `worker` service in Compose). It runs pg-boss 12 in the app database, schema `pgboss`.
- Queues:
  - `embed-item`: one item per job, a singleton per item id, 3 retries with backoff.
  - `embed-sweep`: every minute, queues up to 50 stale items.
  - `prune-search-queries`: weekly.
- After a create or update commits, the items service calls `embedQueue.enqueueIfStale()`. Enqueue failures are logged, never surfaced. The sweep catches anything missed: the worker was down, the model changed, or the item was written before Phase 4.
- `embed-item` loads the item's `search_text` and skips the item if the stored hash still matches. Otherwise it calls the embedder (`EMBEDDING_MODEL`, default `text-embedding-3-small`, 10 s timeout) and writes the vector, model and hash. Every call is logged in `llm_calls`.
- Logs (`jobs/embed-item-log.ts`): one line per job, `[worker] embed <itemId> → embedded|fresh|missing|superseded (Nms)`. A failure is logged before it propagates, so pg-boss retries show up in the log. Sweeps log `sweep queued N stale items` when N > 0.
- Health: the worker touches `/tmp/worker-heartbeat` every 30 s. The Compose healthcheck fails when the file is older than 90 s.
- `pnpm dev` runs the API server and the worker together (`dev:server`, `dev:worker`).

### Web (D79)

- `SearchBox` sits under the deck header on every deck route. It debounces by 250 ms and navigates to `/d/$slug/search?q=&mode=`, replacing the history entry when already on the search route.
- `routes/d.$slug.search.tsx` validates `q` and `mode` (`search/search-params.ts`). It shows one of:
  - `SearchResults`: tags for `why`, highlighted matches, and recent searches when `q` is empty.
  - The lazy `AskView` chunk, when Ask is enabled and selected.
- Search queries use `keepPreviousData` and are excluded from the persisted cache. Search needs the network, and the offline state says so.
- Recent searches (8 per deck) live in `localStorage`.
- Value imports come from `@pb/shared/search`, never the package root, which would pull `mathjs` into the initial chunk.

### Evaluation and demo data (D81, D82)

- `searchCards` in `@pb/db/test`: 40 cards in Hebrew, Greek and English, covering every card type.
- `search-eval.json`: 40 query → expected-key pairs. Kinds: substring, phone, typo, URL, no-result, cross-lingual and meaning.
- `pnpm test:search` (vitest project `search`, `*.search.test.ts`):
  - Loads the deck into a Testcontainers database.
  - Asserts recall@5 ≥ 0.9 for the text arm on the text-capable pairs.
  - Asserts the same for hybrid search on all pairs, when `search-embeddings.json` holds every vector it needs. Vectors are keyed by `sha256(model + text)`.
- `pnpm test:search:update` (needs `OPENROUTER_API_KEY` or `OPENAI_API_KEY`) fills missing cache entries. The file is committed, so CI makes no API calls.
- `pnpm search:load` creates a `search-demo` deck through the API and adds any missing fixture cards (idempotent by title).
- `pnpm search:query "<q>"` prints the hits.
- Both scripts take `--deck`, `--base-url` (or `BASE_URL`) and `--token` (or `SMOKE_SESSION_TOKEN`).

### Deviations from the Phase 4 plan

- **pgvector's built-in Drizzle `vector` type** instead of a custom type.
- **Broader normalization**: the plan asked for lowercase and digits. The SQL also folds the maqaf, Greek tonos and combining marks, so `highlight()` and the database agree.
- **`item_embedding_hash()` in SQL** decides staleness, so enqueue and sweep never compare text in TypeScript.
- **`itemColumns`**: item queries select an explicit column list, so `search_text` and `embedding` never reach DTOs or list queries.
- **`updated_at` trigger narrowed** to user-facing columns (see Data).
- **RRF fused in TypeScript** (`lib/rrf.ts`). SQL returns two ranked arms, which keeps the fusion unit-testable.
- **A heartbeat file for worker health** instead of an HTTP port.
- **`llm_calls.cost_usd` is an estimate** from a price table in code (`ai/llm-calls.ts`). The `claude-haiku-5-5` price is assumed.
- **The Ask rate limit runs before retrieval**, so a limited user costs no query embedding either.
- **Ask is button-triggered** in the PWA (a mutation), not fired while typing.
- **Tests use archived cards as the non-searchable case**, where the plan said draft. Only published cards are searchable.
- **`SEARCH_EVAL_UPDATE=1` / `pnpm test:search:update`** instead of an `--update` flag, which vitest already uses for snapshots.
- **The eval runs against the repository and RRF**, not over HTTP. It's the same ranking code without a server.
- **No embedding cache yet**: `search-embeddings.json` stays `{}` until someone with an embedding key runs `pnpm test:search:update`.
  - Until then the hybrid eval is skipped.
  - Only the text arm is asserted. Its recall is 1.0 on 26 pairs.
- **The search box isn't sticky**, which keeps the sticky chip-row offsets unchanged.
- **The e2e web search tests live in `web.spec.ts`**, because the `web-smoke` project matches only `web|share` specs. The API checks are in `search.spec.ts`.
- **`pnpm test` and `test:coverage` pin their projects** (unit, web, integration). The search project runs only through `test:search`.
- **Fixture cards go into the default category.**
- **`pnpm dev` for the API** runs `dev:server` and `dev:worker` through `pnpm run "/^dev:(server|worker)$/"`.

## Ingestion (Phase 5)

### Data (migration `0009_ingest`)

### Submit (`POST /ingest`)

```
session or ing_ token (ingest-auth, only on this route) → JSON, or multipart with ≤ 3 `files`
  → ingest.service.submit: deck (bound token > deckId > me), item.create, daily caps (per channel + combined → 429),
    images → Cloudinary gobbit/ingest/<deckId> (tags ingest, job:<id>)
  → insert ingest_jobs (queued) → commit → enqueue `ingest {jobId}` (singleton per job) → 202 { id, status }
```

- Body limit 25 MB on `/ingest` only (1 MB elsewhere). Images: JPEG/PNG/WebP/HEIC/HEIF, ≤ 8 MB each.
- No extraction provider (`OPENROUTER_API_KEY` or `ANTHROPIC_API_KEY`) → 503; `/config.ingest.enabled` is false and the PWA hides the share UI.
- Token shares are always `channel = shortcut`; a bound token always ingests into its deck.
- Caps: `jobs.countByUserSince(userId, since, channel?)` over a rolling 24 h. Each channel has its own cap (`ingestDailyCaps()` in `@pb/shared/limits`: `INGEST_DAILY_CAP`, default 50, unless `INGEST_CHANNEL_DAILY_CAPS` overrides the channel), and all channels together stop at `INGEST_COMBINED_DAILY_CAP` (200).
- `GET /ingest/{id}` (sharer or a deck publisher) is the debug view: status, normalized source, extraction summary, dedup verdict, error and Σ `llm_calls.cost_usd` for the job.

### Worker pipeline (`jobs/ingest.ts`)

One pg-boss job runs **fetch → normalize → extract → validate → insert proposed item → embed draft → dedup**, updating `status` between stages. 2 retries with backoff; `ingest-sweep` re-enqueues `queued` jobs older than 5 minutes and fails ones that used every attempt.

- **Fetch** (`fetch/safe-fetch.ts`, ADR-048): undici `Agent` whose `connect.lookup` rejects private, loopback, link-local, CGNAT and metadata addresses (`fetch/ip-guard.ts`, IPv4-mapped IPv6 included). http(s), ports 80/443, ≤ 3 re-checked redirects, 10 s, 3 MB, `text/html` only.
- **Normalize** (`fetch/extract-page.ts`, `fetch/normalize-source.ts`): linkedom + Readability → title, text (≤ 8000 chars), Open Graph, lang. A blocked host, an error or no readable text falls back to OG, then to the shared text (`fetch.fallback` records which).
- **Extract** (`ingest/run-extraction.ts`): `Extractor` implementations for Anthropic and OpenRouter (forced `propose_card` tool) plus a fake for tests. The prompt (`ai/extract-prompt.ts`) holds the deck's categories the **sharer** can see, up to three recent cards as style examples, and the source inside `<source>` delimiters labelled untrusted. Output is validated with the create-item schema + `entitiesSchema` (`ai/extract-validate.ts`); one corrective retry quotes the error; `confidence < 0.6` escalates once to `EXTRACT_ESCALATION_MODEL`. Bodies over 600 characters are cut at a sentence boundary. Types: `text`, `link`, `image` only. The agent never creates categories; it may suggest a `newCategory`.
- **Insert** (`ingest/propose.ts`, shared with direct proposals): a `proposed` item, `created_by` = the sharer (re-checked when the job runs, `ingest/sharer-role.ts`); no fitting category → the deck's default category.
- **Dedup** (`ingest/run-dedup.ts`, `ingest/dedup-verdict.ts`): `embed_draft` embeds the proposal (filling its embedding), then compares with published and proposed items of the deck. Same normalized source URL → `update`; cosine ≥ 0.92 → `update`; 0.80–0.92 → `possible_duplicate`; else `new`. Without an embedding key: URL, then title `word_similarity ≥ 0.8` → `possible_duplicate`. Best-effort: a dedup error leaves `dedup` null. A direct proposal that names its target skips the search: `{ action: 'update', itemId, similarity: null, via: 'explicit' }`.
- Every provider call is recorded in `llm_calls` with `job_id`. Prompts never contain tokens or emails.

### Direct proposals (P5.9)

`ingest.service.proposeDirect({ user, deck, draft, channel, targetItemId?, clientLabel? })` proposes a ready card with no fetch or extraction: resolve the deck, `item.create`, validate the draft (create-item schema, `text | link | image` only, categories the caller can see, optional `newCategory`), check the target (a published card of the same deck the caller can see, else 404), apply the caps, insert a `proposed` job (`extraction.model = 'direct'`, `client_label`), then run the same `proposeItem` step as the worker (default-category fallback, proposed item, dedup verdict, job update, embedding after commit). It has no route yet: the planned MCP server (Phase 13, `docs/plans/mcp-server.md`, D112–D128) calls it with `channel = mcp`, and its edits land in the review queue (D117). Items it creates have `source_kind = mcp`; the review source line reads "shared by Dana via Claude (AI app)".

Non-session tokens are listed in `lib/token-prefixes.ts` (today `ing_`; Phase 13 adds its MCP prefixes). `session-auth` answers 401 for a bearer with a registered prefix on a route that doesn't accept it, without a session lookup. Prefixed tokens are minted and parsed by `lib/prefixed-token.ts`.

### Review (D106, D107)

## Card lifecycle (Phase 6, `specs/006-card-lifecycle`)

Archive, restore, delete and undelete for cards, through one set of service methods that every client shares.

**State machine** (status × `deleted_at`):

```
proposed ──publish (PATCH)──▶ published ──archive──▶ archived
                                  ▲                    │
                                  └──────restore───────┘
published | archived ──delete──▶ deleted (deleted_at set) ──undelete (≤ 30 days)──▶ previous status
deleted > 30 days ──prune-deleted-items (weekly)──▶ hard-deleted
```

**Routes** (session cookie or bearer; `ing_` tokens get 401):

| Route | Permission | Result |
| --- | --- | --- |
| `POST /items/{id}/archive` | `item.archive` (owner, maintainer, editor) | 200 Item, status `archived`; a repeat is a no-op 200 |
| `POST /items/{id}/restore` | `item.archive` | 200 Item, status `published`, `verifiedAt` kept; a repeat is a no-op 200 |
| `DELETE /items/{id}` | `item.delete` (owner, maintainer) | 204; a repeat is 404 (the card is hidden) |
| `POST /items/{id}/undelete` | `item.delete` | 200 Item with its previous status; 410 `undo-expired` after 30 days |
| `GET /decks/{id}/items?status=deleted` | `item.delete` | Cards deleted in the last 30 days, newest deletion first, cursor on `(deleted_at, id)`; no proposals; category visibility applies |

**Decisions**:
- **D130 / ADR-050**: every lifecycle method in `items.service` takes `actor: { user, via: 'session' }` first; routes build it with `getActor(c)`.
- **D131**: `verified_at` is set on the first publication only; restore keeps it. PATCH archived → published is 409 `/problems/use-restore`; archive or restore of a proposal is 409 `/problems/invalid-transition`.
- **D132**: soft delete. Undelete within `ITEM_UNDELETE_DAYS` (30), else 410 `/problems/undo-expired`; a deleted proposal is 404. The worker's weekly `prune-deleted-items` (`DELETED_ITEM_PRUNE_CRON`, Sundays 05:00 UTC) hard-deletes older rows. Migration `0011_item_lifecycle` only adds the partial index `items_deleted_idx (deck_id, deleted_at DESC, id DESC) WHERE deleted_at IS NOT NULL`.
- **D143**: `deckHref(slug, path)` (`apps/web/src/ui/chip-order.ts`) builds every deck-scoped href in the web app.
- **D146**: the web actions are optimistic on the cached lists, roll back on error, invalidate search, and show a 6-second Undo toast after archive and delete. Delete asks first (`window.confirm`). Actions are disabled offline.

**Web**: the card view (`/i/$itemId`) shows Archive/Restore and Delete by role. The Archived view (`/d/$slug/archived`) lists archived cards with Restore and, for `item.delete` roles, a **Recently deleted** section with days left and Undelete. A deleted card's permalink shows "Card unavailable".

### Deviations from the 006 plan

- **`deletedAt` is optional on the Item DTO**, present only on deleted rows (the data model said nullable), so live responses are unchanged.
- **The deleted-list cursor reuses `encodeCursor`** with `deletedAt` in the `createdAt` slot.
- **PATCH proposed → published sets `verifiedAt` only when it is null**; PATCH `status: 'archived'` checks for a proposal before the permission check.
- **Private-category hiding in the deleted listing is tested at the repository level**: every `item.delete` role can read private categories, so no route-level case exists.
- **One web hook (`useLifecycle`) replaces four** (`useArchive`/`useRestore`/`useDelete`/`useUndelete`). The toast store is app-wide (`useSyncExternalStore`) so the toast survives navigation; no new dependency.
- **Optimistic inserts go into every list whose filter decides the card** (all, favorites, archived, deleted) by rank, not only "all"; category lists wait for the refetch. Undoing a restore or undelete shows no toast.
- **The card view navigates back to the deck** after archive or delete.
- **Days left are floored**, so seconds after a deletion the label reads "29 days left".
- **E2E ran locally** against `pnpm dev`; the deployed-instance run (quickstart §5) and the `PLAN.md` demo 2 tick wait for the deploy.

## Card editor (Phase 6, `specs/007-card-editor`)

Create and edit every card type (text, link, table, calc; image is read-only until 008) in one editor with a live preview, local drafts and inline category creation. No API or schema changes and no migration: the editor uses the existing `POST /decks/{id}/items`, `PATCH /items/{id}` and `POST /decks/{id}/categories`.

**Routes (D135)**: create at `/d/$slug/new?type=` (`text` by default; the type picker updates `?type=`), edit at `/i/$itemId/edit` (file `routes/i.$itemId_.edit.tsx`, not nested under the Outlet-less card route; `?from=review` returns to the review queue). Both render `editor/CardEditor`. Edit has no type picker (the type is immutable). The edit route shows "Card unavailable" for a missing, deleted or not-editable card.

**Who sees Edit (R8)**: `canEditItem(item, role, meId)` (`cards/can-edit-item.ts`) mirrors the API: `item.update`, and for a proposal also `item.publish` or being its creator (D96); never a deleted card. `EditLink` renders on the card page, in the archived list (inside `CardActions`) and on the live lists (through `DeckItems`' `renderActions`); review cards get "Edit fully".

**Preview (D136)**: `EditorPreview` renders the draft through `cards/Card` in `preview` mode (no favorite, share, actions or links), so the list and the preview share one renderer. Phones get Edit/Preview tabs (`EditorTabs`); at ≥ 768 px the two sit side by side (CSS only).

**Draft model (D137)**: `editor/draft.ts`: `Draft`, `emptyDraft(type, defaultCategoryId)`, `draftFromItem(item)`, `withType`, `toCreateBody(draft)` and `toPatch(original, draft)` (minimal diff, whole `payload`/`entities` when changed, `null` when unchanged). The review queue's inline edit (`ReviewEditForm`) uses the same model and fields; `review-edit.ts` is gone. Saving goes through `use-save-card.ts` → `api/create-item.ts` / `api/update-item.ts` (one PATCH hook for the editor and the review queue; R9 cache rules: set the item (and its review-queue entry), invalidate the item lists and search, and the review queue when a proposal was saved). Server field errors map back to fields through `problem-fields.ts`.

**Field registry (D138)**: `editor/fields/registry.ts` maps each type to a lazy fields component (`TextFields`, `LinkFields` with a `previewSlot` seam for 008, `TableFields` up to 12 × 6 with up/down reorder and a byte meter, `CalcFields` up to 6 fields with a live result, `ReadOnlyImage`, replaced by `ImageFields` in 008). Shared fields: `TitleField`, `BodyField` (with `LimitMeter`), `CategoryChips` (at least one; inline **New category** when `can(role, 'category.create')`, which posts with the default `shared` visibility and selects the same-named visible category on a 409), `SourceUrlField` and remove-only `EntityChips`.

**Client validation (R6)**: `editor/validate.ts` mirrors the server limits without zod (title, body ≤ 600 code points, payload ≤ 8192 UTF-8 bytes, URLs, table and calc shapes) using value imports from `@pb/shared/card-limits` only. Calc expressions are checked by `@pb/shared/calc`, loaded with a dynamic import while the type is calc (`use-calc-check.ts`), so mathjs stays in its async chunk. The server stays authoritative; its problem details are shown as they come.

**Drafts (D145)**: `editor/drafts-store.ts` on idb-keyval (`createStore('gobbit-drafts', 'drafts')`, behind a `DraftsKv` interface). Keys `new:<deckId>:<type>` and `edit:<itemId>`, value `{ draft, baseUpdatedAt, savedAt }`. `use-draft-autosave.ts` writes 500 ms after the last change, offers a restore on open (`DraftRestoreBanner`, with a "card changed since" warning when the server `updatedAt` is newer than `baseUpdatedAt`), and deletes the draft on save, on discard and when the draft returns to its opening state. `signOut` calls `clearDrafts()` (loaded on demand) after clearing the persisted cache. Storage failures are logged and never block editing.

**Bundle**: initial JS 111.5 → 112.5 KB gzip. The editor, its fields and the drafts store are route or on-demand chunks; `editor/creatable-types.ts` keeps the draft model out of the `/d/$slug/new` route's initial import.

**No new dependencies (R7).**

The live lists (all, category, favorites) have no actions slot in use, so 007 passes `renderActions` from `DeckItems` for them too, rendering `EditLink` there. ## Card media (Phase 6, `specs/008-card-media`)

Image cards from the editor (upload a photo, or take one on a phone) and "Fetch preview" for link cards. Two new routes, no migration, no new env vars and no new dependencies (`cloudinary` and `lru-cache` were already in the API).

**Boundary with Phase 7 (D129)**: Phase 6 ships signed browser uploads and a synchronous link preview, both as services. The `assets` table, the orphan sweep, remote-URL upload, preview snapshots, link checks and `CloudImage` stay in Phase 7. An image card stores only `{ publicId, alt }`; an upload whose card is never saved stays in Cloudinary until Phase 7's sweep, which can find it by tag.

**Signed direct uploads (D133, ADR-051)**: `POST /decks/{id}/media/sign` (`media.service` → `media/sign-upload.ts`). Access: `resolveDeck` + `authorize(..., 'item.create')`; then 503 `/problems/unavailable` without `CLOUDINARY_URL`; then `rateKeys.mediaSignUser` at 60/user/hour. The response holds the upload URL, `apiKey`, `timestamp`, `signature`, `folder`, `tags`, `allowedFormats`, `maxBytes` and `expiresAt` (50 min, inside Cloudinary's one-hour signature window), with `Cache-Control: no-store`. The API secret never leaves `signEditorUpload`. The browser posts the file straight to `https://api.cloudinary.com/v1_1/<cloud>/image/upload` (`editor/upload.ts`, XHR for progress and abort); the API never sees the bytes. The web CSP `connect-src` adds `https://api.cloudinary.com` (`apps/web/Caddyfile`).

**Storage conventions**: folder `gobbit/items/<deckId>` (ingest uses `gobbit/ingest/<deckId>`), tags `editor` and `deck:<deckId>`, formats jpg/png/webp/heic/heif. All of them are covered by the signature, so the browser can't change them. 8 MB (`MEDIA_IMAGE_MAX_BYTES`, the same as ingest) is checked in the browser before the upload; Cloudinary's account upload limit is the server-side backstop (no signed preset, see Deviations).

**Editor image fields**: `editor/fields/ImageFields.tsx` replaces `ReadOnlyImage`; image is in `CREATABLE_TYPES`. "Take photo" (`capture="environment"`) and "Choose photo" are labelled file inputs; `image-file.ts` checks the type (MIME, or the extension when the browser reports none, e.g. HEIC) and size. `use-image-upload.ts` runs sign → upload with states idle / signing / uploading (percent) / failed (with retry), cancel through `AbortController`, and maps 429/503/403/404 to messages. `cachedSigner` reuses a signature until it expires; a stale signature is re-signed once. `validate.ts` requires a finished upload ("Add a photo") and alt text ("Alt text is required"). Without a cloud name (`GET /config`) the type picker disables Image with "Image cards aren't available: image storage isn't set up here." and `?type=image` falls back to text. Offline, picking is disabled.

**Link preview (D134)**: `POST /decks/{id}/link-preview` (`link-preview.service`): `item.create`, then `rateKeys.linkPreviewUser` at 30/user/hour, then an `lru-cache` (200 entries, 1 h, keyed by the parsed URL; empty results are cached too). The page is fetched only through `fetch/safe-fetch.ts` (ADR-048) and read by `extract-page`: OG title (else `<title>`, ≤ 200 code points), OG description (≤ 500), absolute http(s) OG image (≤ 2048 chars). Any failure answers `200 { preview: null }`; the reason is only logged. In the editor, `LinkEditorFields` puts `FetchPreview` in the 007 `previewSlot`: text the member already wrote wins over fetched text, a fetched image replaces the old one, and an empty card title takes the fetched title. Any failure reads "No preview available" and Save stays on.

**Bundle**: initial JS unchanged at 112.5 KB gzip; the image and preview code sits in the editor's lazy chunks (`CardEditor` chunk 7.4 KB gzip). Web code imports the zod-free `@pb/shared/media-constants`.

### Deviations from the 008 plan

- **8 MB, not 10 MB**: the same cap as ingest images (`INGEST_IMAGE_MAX_BYTES`).
- **No width/height** in the image payload: the card stores `{ publicId, alt }` only, as the existing schema does.
- **No `siteName`** in the preview: the link payload has no field for it, so it is dropped.
- **The fetch failure reason is not returned** (`{ preview: null }`), only logged, so the route can't be used to probe hosts.
- **No signed upload preset**: signed params alone (folder, tags, formats) plus the client-side 8 MB check; Cloudinary's account limit is the backstop. A signed preset with a size cap can be added later by signing its name.
- **Schemas in `schemas/media.ts`**, exported from `@pb/shared` and `@pb/shared/media`; the web imports the zod-free `@pb/shared/media-constants` (research named `@pb/shared/media`).
- **`LINK_PREVIEW_IMAGE_URL_MAX` = 2048** is new: longer image URLs are dropped.
- **Order of checks**: access before the rate limit on both routes; the sign route's 503 comes after the access check and before the rate limit, so a server without Cloudinary doesn't use up a member's hourly count. The preview rate limit counts cache hits too.
- **Upload state**: starting an upload clears the stored `publicId`, so cancelling or failing a replacement leaves no photo (Save then asks for one). A restored draft keeps only a finished `publicId`.
- **Alt text has no client maximum**: the server has none either; the 8192-byte payload limit covers it.
- **Fetch preview only in the card editor**, not in the review queue's inline edit (which keeps plain `LinkFields`).
- **E2E fakes Cloudinary**: the smoke specs answer `/api/config` (cloud name), `/api/decks/*/media/sign`, `api.cloudinary.com` and `res.cloudinary.com` with `page.route`, so no test talks to Cloudinary or needs credentials. The happy-path preview is faked too, because `safe-fetch` refuses the local fixture server the task described; the no-preview path goes through the real API with a private-IP URL.
- **Caddy's `Permissions-Policy: camera=()`** stays: it doesn't affect `<input capture>`, which opens the system camera.
- **`use-image-upload.ts` is not a TanStack mutation**: sign and upload are one sequence with progress, cancel and one re-sign, so the hook keeps its own state behind an injectable `Signer` and upload function.
- **`ImageCard` is keyed by `publicId`** in `CardBody`, so a replaced photo in the editor preview doesn't inherit the previous photo's load error.

## Browse mode (Phase 6, `specs/009-browse-mode`)

Browse shows one card per screen. Readers swipe vertically between cards, across the header to change category, and across the footer to switch between the Content, Details and Source panes. Every gesture has a button and a key. Nothing changes in the API or the DB. The one new web dependency is `@use-gesture/react`, and it loads only in the Browse chunk.

**Route and address (D141)**:
- The route is `/d/$slug/browse?c=<all|category>&i=<itemId>&pane=<content|details|source>` (`routes/d.$slug.browse.tsx`).
- `browse/browse-params.ts` parses the search params leniently and has no zod: unknown values fall back to the defaults.
- While browsing, `DeckLayout` renders only its `<Outlet>`. `isBrowsePath()` detects the route.
- Card, category and pane changes `replace` the history entry, so only opening Browse adds one.
- The "Browse" button sits on the All and category lists (`items/BrowseButton.tsx`). It opens Browse on the first card visible in the list (`items/first-visible.ts`) and pushes with `state.fromList`, which carries the list's category.
- Closing (button or Escape):
  - from the same category, `history.back()`;
  - after a category change, the list of the new category replaces the Browse entry;
  - from a deep link, the list is pushed.
- The system back action after a category change (FR-005): Browse records the opening list and its history index (`__TSR_index` − 1) in `sessionStorage` (`gobbit:browse-opener`). When that exact entry mounts again and the return entry names another category, `ItemList` replaces it with the current category's list, which then scrolls to the card.

**Data**:
- `browse/use-browse-items.ts` runs `useInfiniteQuery(itemsQuery(slug, filter))` with the list's own filter. Browse and the list share the cache and the persisted offline copy.
- The next page is fetched 3 cards before the end.
- A deep-linked `i` is searched for across up to 5 pages. If it isn't found, Browse opens on the first card with "That card isn't available here".
- Archived, deleted, proposed and hidden cards are never in the list query.

**Paging (D139, D144)**:
- `.browse__pages` is a native CSS scroll-snap container: `y mandatory`, with `overscroll-behavior-y: contain`.
- Every page is `100dvh`. Only the current card ±1 render content; the rest are empty placeholders of the same height.
- One IntersectionObserver at threshold 0.6 (`use-current-card.ts`) tracks the current card. After 300 ms of settle it writes `i`.
- Only the current page is exposed to assistive tech; the others are `inert` + `aria-hidden`. Focus moves to the card title on change, and one live region announces the position.
- **Scroll restoration is disabled for this route** (`app/router.ts`). Router scroll restoration would otherwise restore the snap container from an earlier Browse visit in the tab, and again after every settle `replace`. Browse positions itself only from `i`.

**Zones (D140)**:
- The header band (`max(25dvh, 88px)`) and the footer band take horizontal swipes through `use-zone-swipe.ts` (`useDrag`, `axis: 'x'`, `filterTaps`, `touch-action: pan-y`).
- `swipe.ts` classifies a swipe: at least 40 px or 0.3 px/ms, on the dominant axis, with leftward meaning next.
- The 24 px at each screen edge are ignored (`edge-guard.ts`), so the system back gesture keeps working.
- The middle zone only scrolls.
- Category order is All, then the chip-row order (`category-cycle.ts`), with no wrap-around.
- The footer selects the pane, and the pane stays the same across cards. The Content pane is the list's card (favorite, share, and the title links to `/i/<id>`).

**Without gestures (D142)**:
- Buttons: ↑/↓ card buttons, ‹ › category chevrons named after their target, a category menu, a `tablist` for the panes, and a close button.
- Keys: PageUp/PageDown/ArrowUp/ArrowDown for cards, ArrowLeft/ArrowRight for categories, Escape to close. The pure classifier in `browse-keys.ts` skips inputs and card bodies that can still scroll.
- A first-run dialog ("How to browse") explains the zones. Its dismissal is remembered in `localStorage` `gobbit:browse-hint:v1`.
- Under `prefers-reduced-motion`, card changes scroll with `behavior: 'auto'`.

**Return to the list (FR-005)**:
- Every card change writes `{ deckSlug, filterKey, itemId }` to `sessionStorage` (`browse-return.ts`).
- `ItemList` reads the entry once on mount. If it matches the list's deck and filter, it scrolls that card into view and clears the entry. This overrides the pathname-keyed restore (D65) only for that one return.

**Images and motion (D144)**:
- `ImageCard` has optional `sizes` and `priority` props. Browse passes a viewport-based `sizes` (`use-image-sizes.ts`).
- The current card gets `loading="eager"` + `fetchpriority="high"`; its neighbours stay lazy.
- The only CSS transition is a `transform` on the footer dots, so there is no `will-change`. Styles live in `browse/browse.css`, which is part of the lazy chunk.

**Bundle**:
- Initial JS is 113.7 KB gzip (was 112.5).
- The Browse route chunk is 13.1 KB gzip, including use-gesture's `useDrag` (~8.5 KB).
- `pnpm budget` fails if an initial chunk contains `@use-gesture` code. `scripts/initial-chunks.ts` `lazyOnlyViolations` checks for content markers.

### Deviations from the 009 plan

- **The return entry is written immediately** on each current-card change, not debounced to 300 ms. `current` already trails scrolling through the observer.
- **CSS is in `browse/browse.css`**, with its own reduced-motion block, not in `styles.css`. It stays out of the initial CSS.
- **Scroll restoration is disabled on `/d/$slug/browse`**. The plan assumed D65 only affected the list.
- **`isBrowsePath()` is a regex**, not `pathname.endsWith('/browse')`, which would misfire on a category whose slug is `browse`.
- **Close after a category change replaces the entry with the new category's list.** The system back action lands on the opening list, which redirects (`replace`) to the current category's list via the opener record and history index (convergence T052).
- **The not-found notice stays** while the reader is on the card Browse opened on, even after `i` is written.
- **The lazy-only check matches content markers**, because production chunks carry no module paths.
- **E2E swipes use CDP `Input.dispatchTouchEvent`** (`e2e/tests/smoke/helpers/swipe.ts`), because Playwright's touchscreen API only taps.
- **Accessible names are asserted with `getByRole`**; there is no axe dependency. The research also recorded plan-vs-code resolutions, all resolved in favour of the code:
  - an auto-split file route instead of an explicit lazy import;
  - reusing `cards/cloudinary.ts` widths;
  - the `gobbit:browse-hint:v1` key;
  - a Source pane built from `sourceKind`/`sourceUrl`/ages.

## Architecture Decision Record

### ADR-001: Millisecond-precision timestamps for keyset cursors

**Decision**: All `timestamptz` columns use `precision: 3`.

**Rationale**: JavaScript `Date` is millisecond-based. Keyset pagination encodes `(createdAt, id)` in the cursor. If DB precision is microsecond but JS rounds to ms, the cursor may round-trip incorrectly, causing duplicates or gaps. Fixing precision at ms guarantees accurate serialization.

---

### ADR-002: Vitest test.projects instead of vitest.workspace

**Decision**: Root `vitest.config.ts` defines two test.projects (unit, integration) instead of separate workspace packages.

**Rationale**: 
- Simpler coverage thresholds (one config applies to all)
- Integration tests can safely use globalSetup (Testcontainers) without interfering with unit tests
- Single command `pnpm test` runs all; `pnpm test:unit` or `pnpm test:int` filters by project
- FileParallelism=false for integration tests (sequential DB access); unit tests run in parallel

---

### ADR-003: TypeScript source exports, no build step

**Decision**: Packages export `.ts` files directly from `src/`, evaluated at runtime via `tsx`.

**Rationale**:
- Faster iteration: change src, tests pick it up immediately
- Single source of truth: no divergence between src and build output
- Simpler tooling: no tsconfig build path mappings, no esbuild config
- Type checking: `tsc --noEmit` validates syntax; runtime safety from Zod at boundaries

**Trade-off**: Slightly slower runtime (tsx transpiles on-the-fly), acceptable for Phase 1 API server; Web frontend (Phase 3) will bundle.

---

### ADR-004: 404 for foreign decks, not 403

**Decision**: When a user accesses a deck they don't own, return 404 (not found), not 403 (forbidden).

**Rationale**:
- Doesn't leak information about which resources exist
- Consistent with "access control as query filter" pattern (repository only sees user's own data)
- Phase 2 can refine to shared/public decks; 404 still applies to truly private ones

**Implementation**: Phase 1 used `assertDeckAccess()`; since Phase 2 `authorize()` (`access/authorize.ts`) throws `notFound()` when the caller has no role on the deck (D35), and 403 only when a role lacks the permission.

---

### ADR-005: Soft deletes via `deleted_at` timestamp

**Decision**: Never physically remove rows; set `deleted_at = now()`.

**Rationale**:
- Audit trail: can query deleted items if needed
- Foreign key safety: references don't break if a category is deleted
- Reversible: undelete possible (though not exposed in Phase 1 API)
- Compliance: supports data retention policies

**Query pattern**: All reads include `WHERE deleted_at IS NULL`.

---

### ADR-006: Denormalized deck_id in item_categories

**Decision**: `item_categories` table includes `deck_id` even though it's redundant (reachable via itemId → items → deckId).

**Rationale**:
- Enables composite foreign key: `FK(itemId, deckId) → items(id, deckId)`
- Prevents a bug where an item_category references an item in a different deck
- Marginal storage cost, significant constraint benefit

---

### ADR-007: Default category auto-created and protected

**Decision**: Every deck gets an automatic 'general' category on insert. Cannot be deleted or modified to `is_default=false`.

**Rationale**:
- UX: users always have at least one category to tag items
- Safety: avoids "item with no categories and status=published" edge case
- Database enforces via trigger + unique index, not app logic

**Cascade exception**: When deck is deleted, the trigger cleanup is allowed (pg_trigger_depth > 1 check).

---

### ADR-008: Payload validation in @pb/shared, re-validated on PATCH

**Decision**: `payloadSchemaFor(type)` lives in @pb/shared. Service re-validates payload on PATCH.

**Rationale**:
- Schema is single source of truth for all consumers (API, tests, migrations)
- PATCH may not provide type (immutable), so service must know which schema applies
- Validation failure → 400, not 422 (matches Zod error convention)

---

### ADR-009: Limit >50 rejects, doesn't clamp

**Decision**: `limitSchema` rejects values >50 with a validation error, never silently reduces.

**Rationale**:
- Explicit: client knows the constraint
- Prevents accidental large result sets (DoS risk)
- Encourages clients to paginate properly

---

### ADR-010: RFC 9457 Problem+JSON for all errors

**Decision**: API always returns error responses as `application/problem+json` with type, status, title, detail, errors.

**Rationale**:
- Standardized: clients can parse error details uniformly
- OpenAPI: schema documented in /openapi.json
- Field errors: Zod validation failures list path + message for each field
- Type URL: clients can decide action (409 /conflict ≠ 422 /constraint-violation)

---

### ADR-011: Migration rollback via .down.sql

**Decision**: Each migration can be rolled back; down file executed in a transaction, then journal entry deleted.

**Rationale**:
- Not every migration is reversible (data loss possible), but metadata changes (add column) are
- Hand-written down files are explicit, not auto-generated (forces thinking)
- Single transaction: either fully rolls back or fails atomically
- Emergency recovery: can revert to prior schema without manual intervention

---

### ADR-012: Seed with uuid v5 namespace

**Decision**: Deterministic IDs via `v5(key, SEED_NAMESPACE)`.

**Rationale**:
- Reproducible: same seed produces same IDs every run
- Testable: suites assert on stable ids like `fixtureId('deck/family')` (since D49 these come from test factories, not the seed)
- No collisions: different keys hash to different IDs
- Never in production: seed only used in dev/test (guarded by env check)

---

### ADR-013: Pagination cursor encodes (createdAt, id)

**Decision**: Keyset cursor is base64url-encoded JSON: `{ c: isoString, i: uuid }`.

**Rationale**:
- Immutable sort: createdAt + id is unique, immutable per-row
- Doesn't count results: scales to large tables
- Works with DESC order: clients naturally iterate forwards in time
- Human-readable when decoded

**Alternative considered**: Offset pagination (simple, bad for large tables).

---

### ADR-014: Calc expression validation with mathjs walk, no evaluation

**Decision**: `validateCalcExpression()` parses expression tree, walks nodes to check allowed functions/symbols. Never evaluates.

**Rationale**:
- Safety: code evaluation is a security risk
- Deterministic: validation is stable (no random number gen affecting outcome)
- Error messages: can report specific disallowed functions
- Phase 2: server-side evaluation can safely use validated expressions

---

### ADR-015: Item type immutable, idempotent favorites

**Decision**: PATCH rejects if `'type' in patch` (400 bad-request). Favorite add/remove is idempotent.

**Rationale**:
- Type change would require payload migration (complex), so forbid it
- Idempotence: `POST /items/{id}/favorite` twice is safe (onConflictDoNothing), `DELETE` twice is safe (no error on missing)
- Phase 2: if client retries a request, idempotence prevents duplicates

---

### ADR-016: Dev auth middleware with constant-time comparison

**Status**: Superseded by ADR-025 and ADR-031 (Phase 2).

**Decision**: Dev token validated via `timingSafeEqual`, length checked first. Removed in Phase 2.

**Rationale**:
- Timing attack resistance: attacker can't infer token char-by-char from timing
- Phase 1 scaffold: simple bearer + header, no sessions, no magic links
- Secure default: even in dev, follow crypto best practices
- Bypass list: /health and /openapi.json for liveness/discovery

---

### ADR-017: Access control in service layer

**Decision**: access is checked in the service layer. Phase 1: `assertDeckAccess(user, deck, action)` (ownership). Phase 2: `authorize(user, deck, permission, memberships)` — `resolveRole()` + `can()` — called by every service method that touches a deck.

**Rationale**:
- Centralized: consistent policy across routes
- Fail-safe: throws 404 not found (doesn't expose existence)
- Extensible: Phase 2 added `can()` granularity via `authorize()` (see Authorization)

---

### ADR-018: Problem schema with optional field errors, pg error mapping

**Decision**: `Problem` includes optional `errors: ProblemFieldError[]`. `mapPgError()` detects constraint codes and returns mapped Problem.

**Rationale**:
- Field errors: Zod validation can report path + message per field
- Pg error mapping: 23505 (unique) → 409, 23514 (check) → 422, P0001 (custom) → varies
- No SQL leakage: error message sanitized, constraint name omitted from response

---

### ADR-019: Migration journal↔__drizzle_migrations sync

**Decision**: `migrations/meta/_journal.json` is the source of truth. `__drizzle_migrations` table is drizzle's internal state. `getLatestMigrationTag()` matches `when` (ms) between them.

**Rationale**:
- Drizzle creates __drizzle_migrations; we can't control its schema
- Journal is our integration point: stable, human-readable
- Matching on timestamp: every migration is timestamped, can find it in both places
- Rollback: deletes from __drizzle_migrations, doesn't touch journal (audit trail)

---

### ADR-020: Testcontainers PostgreSQL with template DB cloning

**Decision**: Global setup creates `template_pb` with all migrations. Each test clones it. Integration tests in isolation, fast.

**Rationale**:
- Parallelizable: tests can run independently (each has own DB)
- Fast: clone is faster than rerunning migrations per-test
- Reliable: clean slate per test (no test-to-test pollution)
- Scalable: CI can use `-j` to run tests in parallel

---

### ADR-021: Smoke tests with @smoke tag and health wait

**Decision**: E2E tests tagged `@smoke` each work in their own `smoke-<id>` deck (D50). Global setup waits for `/health` ok=true + migration tag match.

**Rationale**:
- Isolation: smoke tests use dedicated deck (don't interfere with other tests)
- Readiness: wait for health ensures DB migrations are done before tests start
- Reproducible: tag makes `pnpm test:e2e --grep @smoke` work

---

### ADR-022: Toolchain notes from the Phase 1 build

**Decisions**:
- **pnpm 11 build approval** uses the `allowBuilds:` map in `pnpm-workspace.yaml` (esbuild allowed; cpu-features, protobufjs, ssh2 denied). `onlyBuiltDependencies` is not honoured by pnpm 11.
- **Vitest `test.projects`** in the root `vitest.config.ts` replaces the deprecated `vitest.workspace` file.
- **Root devDeps for integration globalSetup**: `@testcontainers/postgresql`, `testcontainers`, `pg`, `drizzle-orm` are also declared at the root. Vitest resolves bare imports in a project's `globalSetup` from the workspace root, not the importing package.
- **`noUncheckedIndexedAccess` off**: it produced ~100 noise errors on array/row access across tests and repos. Row lookups rely on explicit guards (`if (!row) throw notFound()`).
- **HTTP error helpers return** an `HttpError` and callers `throw` them (`throw notFound()`), so control flow is visible to TypeScript.
- **pg pool `error` listener** in `createPool`: idle clients killed server-side (restart, `DROP DATABASE ... WITH (FORCE)`) would otherwise surface as an uncaught exception. `57P01` is ignored, everything else is logged.

### ADR-023: Open-source repository hygiene

**Decisions**:
- **Private notes stay local**: `plans/` (personal planning docs) and `docs/thrifty/` (AI build artifacts: prompts, per-sprint cost manifests) are gitignored. The public roadmap is the neutral `PLAN.md`. (Amended by ADR-049: from Phase 6, feature specs and plans are committed under `specs/`; `plans/` remains for private scratch.)
- **No personal data in fixtures**: seed data and tests use `example.test` emails and generic households only.
- **CI on GitHub-hosted runners**: `ci.yml` runs on `ubuntu-latest` so fork PRs never execute on a private machine. `smoke.yml` (main only, targets the deployed API) picks its runner from the `SMOKE_RUNNER` repo variable, defaulting to `ubuntu-latest`, and is skipped while `API_BASE_URL` is unset. Actions are pinned to their latest major tags (Node 24 runtime); pnpm comes from `packageManager`, Node from `.nvmrc`.
- **E2E env resolution** (`e2e/lib/env.ts`): GitHub passes unset vars/secrets as empty strings, so blank values are treated as unset; `BASE_URL` must be an http(s) URL, and a missing one fails fast under `CI`.
- **Standard community files**: `CONTRIBUTING.md`, `SECURITY.md` (GitHub private vulnerability reporting, no personal email), `CODE_OF_CONDUCT.md` (Contributor Covenant 2.1), issue templates. No PR template, so a new PR takes its title and body from the commit.
- **License: MPL-2.0** (file-level copyleft): changes to project files are shared back, while the code can still be combined with proprietary code. Root `LICENSE` holds the full text; every `package.json` declares `"license": "MPL-2.0"`.
- **`"private": true` stays** in every `package.json`: it only blocks accidental npm publishing of this app monorepo.

### ADR-024: Rename pocketbook → deck, rewrite migrations in place, owner-only seed (D48–D50)

**Decisions**:
- The domain noun is **deck** everywhere: tables (`decks`, `deck_id`, enum `deck_kind`), constraint names, schemas, routes (`/decks…`) and docs. The product is **Gobbit**; the repository name is unchanged.
- **Migrations were rewritten in place** (`0001_core`, `0002_invariants`, `0003_card_limits` and their `down/` files) with the same tags, rather than adding a rename migration. This was safe because no deployed database held user data at the time: Phase 1 only ever ran against disposable dev, CI and seeded smoke databases, all of which are recreated from scratch. Any existing local database must be dropped and re-migrated.
- **Seed reset**: the seed creates only the owner user (see Seeding). Fake users and sample cards moved to test fixtures, so the deployed database contains no fabricated people.
- **`DELETE /decks/:id`** (soft delete; the partial unique index frees the slug) was added so the smoke suite can create a `smoke-<runId>` deck per test and remove it afterwards, leaving the deployed database as found.

---

### ADR-025: Opaque server-side sessions over JWT (D22, D27)

**Decision**: Sessions are random 32-byte tokens; only their sha256 is stored. Cookie and bearer sessions are both rows in `sessions`.

**Rationale**: Logout and "log out everywhere" are one `UPDATE`; no signing-key rotation or token blacklist; a DB leak yields no usable tokens. The cost (one indexed lookup per request) is negligible at this scale.

---

### ADR-026: Atomic single-use magic links (D23)

**Decision**: Consumption is a single conditional `UPDATE … RETURNING`; the failure reason is computed only afterwards.

**Rationale**: Two concurrent clicks can't both succeed, and there is no read-then-write race window.

---

### ADR-027: An invite creates the user (D25, D37)

**Decision**: `POST /decks/:id/invites` calls `findOrCreateByEmail()`, so a pending membership always has a non-null `user_id`.

**Rationale**: One code path creates users (Phase 9 can gate registration there); memberships stay simple FKs; the invite link only has to accept.

---

### ADR-028: Implicit owner via the account (D33)

**Decision**: Users of a deck's `owner_account_id` are `owner` without a membership row; a trigger forbids giving them one.

**Rationale**: Personal decks need no membership bookkeeping, and there is exactly one source of truth per user–deck pair.

---

### ADR-029: DTO category filtering (D38)

**Decision**: The item DTO's `categoryIds` is filtered by the same visibility predicate as the queries.

**Rationale**: A card shared with a reader must not leak the ids of private categories it is also filed under.

---

### ADR-030: Postgres rate limiting (D39)

**Decision**: Fixed-window counters in `rate_limit_counters`, no Redis.

**Rationale**: One fewer service to run; the atomic upsert is correct under concurrency; volumes are tiny. pg-boss (Phase 4) can take over the cleanup.

---

### ADR-031: Dev auth deleted, not flagged off (D43)

**Decision**: The dev-token flag, token variable, user header and middleware are removed. The smoke suite authenticates with a real owner bearer session (`SMOKE_SESSION_TOKEN`): seeded locally, minted with `/auth/token-exchange` on the deployed instance.

**Rationale**: A dormant bypass is a latent vulnerability; the smoke suite now exercises the real session path end to end.

---

### ADR-032: Owner-only seed with test factories (D49)

**Decision**: The seed creates only the owner (plus the optional smoke session); integration and smoke tests build their own data with `@pb/db/test` factories or per-test `smoke-<id>` decks.

**Rationale**: The deployed database contains no fabricated people or cards, and tests don't depend on shared mutable state.

**Update (Oct 1)**: the seed is local-only and refuses production; the deployed database is never seeded.

---

### ADR-033: Deploy the CI-built image; `/health` reports the commit

**Decision**: CI builds the API image once (with `GIT_SHA`), pushes it to GHCR and calls the Dokploy deploy webhook; Dokploy runs that image (`infra/docker-compose.yml`, `pull_policy: always`) on Dokploy's `dokploy-network`, behind the shared `cloudflared` → Traefik route. `/health` returns `commit`, and the smoke workflow waits for the commit it was triggered by before testing.

**Rationale**: The image that passed CI is the one that runs (no second build on the box), the same pattern as the owner's other Dokploy apps, and smoke can't pass against the previous container.

---

### ADR-034: The web image owns static files and routing (D51, D54)

**Decision**: The PWA is built to static files in a `node:22-slim` stage and served by `caddy:2-alpine`. Its `Caddyfile` routes `/api/*` (stripped) and `/s/*` to `api:3000`, serves files with the cache headers and CSP from D54, and falls back to `index.html`.

**Rationale**: The API never serves UI, routing is versioned with the code, and Traefik needs one router. Caddy gives compression, headers and SPA fallback in a few lines.

---

### ADR-035: Generated API client from the OpenAPI document (D53)

**Decision**: `pnpm api:openapi` builds the app with stub dependencies, writes `packages/api-client/openapi.json` and generates `schema.d.ts` with `openapi-typescript`. The web app uses `openapi-fetch` and `openapi-react-query`. CI regenerates and fails on any diff.

**Rationale**: Types come from the contract the API actually serves, at a few KB of runtime, and a future native app can reuse the package.

---

### ADR-036: Offline through the query cache, not the service worker (D56)

**Decision**: The service worker precaches the shell and caches Cloudinary images only. API data persists through TanStack Query to IndexedDB (7 days, busted by commit) and is removed on sign-out.

**Rationale**: The query layer knows freshness and failures, so the offline banner is accurate. No cookie-scoped responses sit in a cache that outlives the session. This replaces the master plan's Workbox stale-while-revalidate for API `GET`s.

---

### ADR-037: Share previews: one URL, public or private, lazily rendered images (D58–D61)

**Decision**: `/s/:itemId` always returns 200. Public items (published, public deck, a public category) get real title, excerpt and image; anything else gets the same generic page. Card images are rendered on the first request (Satori + resvg), uploaded to Cloudinary under a content-hashed public id and recorded in `og_images`. The private image is static and committed.

**Rationale**: Existence never leaks (ADR-004). The content hash in the image URL busts WhatsApp and Telegram caches after an edit. One render per share needs no job queue before Phase 4.

---

### ADR-038: Minimal Dokploy configuration (D52)

**Decision**: Every non-secret deployed value is a default in `infra/docker-compose.yml`; `docker-compose.local.yml` overrides them for localhost. Dokploy holds only the Compose source, the secrets (`DATABASE_URL`, `RESEND_API_KEY`, `CLOUDINARY_URL`), the deploy webhook and backups. Traefik gets one router from labels on `web`.

**Rationale**: The repo decides what runs where. A redeploy can't drift from what's reviewed.

---

### ADR-039: Shared Postgres outside the Compose project (D67)

**Decision**: The deployed Compose project has no database. The API connects with `DATABASE_URL` (a Dokploy secret) to a shared pgvector Postgres used by several services, each with its own database and least-privilege owner role (`gobbit`). Today it is a Dokploy-managed database reached over the LAN on its external port. A later move to a cloud provider changes only the URL (`sslmode=verify-full` off the LAN). Extensions are created once by the instance's superuser; migration 0000's `CREATE EXTENSION IF NOT EXISTS` is then a no-op. `docker-compose.local.yml` adds a local `db` service for `pnpm compose:up`, and `docker-entrypoint.sh` refuses to start without `DATABASE_URL`. `api` stays off `dokploy-network`, where another project's `api` service could shadow Caddy's `api:3000` upstream.

**Rationale**: One instance for many small services saves memory and maintenance. Dokploy's database backups work on managed databases, not on Postgres inside a Compose project. A URL is also the portable boundary for moving to the cloud. The cost: Gobbit shares the instance's Postgres major version and its failures, so local and integration tests (pg17) should track the shared instance's major version.

---

### ADR-040: Personal deck ensured on every sign-in, addressed as `me` (Phase 3B)

**Decision**: Each account has exactly one personal deck, marked `decks.is_default` and protected by a partial unique index, a trigger and CHECKs. `usersService.ensurePersonalDeck()` runs inside the magic-link callback transaction on every sign-in and invite, before the session opens. Its public address is `me`: a reserved slug that the API resolves and the PWA shows as `/d/me`. The stored slug is `personal-<accountId>` and is never shown. There is no backfill migration.

**Rationale**: "Ensure" on every callback covers new users, invitees and accounts created before this phase without a data migration. It sits next to `findOrCreateByEmail()`, so the Phase 9 registration gate covers it too. Running it in the callback transaction means no user reaches the app without a deck, and a failure leaves no session behind. Finding the deck by `is_default` rather than `kind` stays correct when other personal decks exist. A fixed alias keeps URLs stable across renames and asks the user for no slug.

---

### ADR-041: Hybrid search in one repository call, fused in TypeScript (D68–D71)

**Decision**: Search uses Postgres only, with two arms on a generated `search_text` column:
- a trigram and substring arm;
- a pgvector cosine arm.

`searchRepo.hybrid()` runs both arms under the same deck, status and category-visibility filters. `lib/rrf.ts` fuses them with reciprocal rank fusion (k = 60).

**Rationale**: Family decks are small (hundreds of cards), so a separate search engine would add operations work without better results. The two arms cover each other's gaps:
- Trigrams catch phone numbers, typos and mixed scripts that embeddings miss.
- Vectors catch meaning and cross-lingual queries that trigrams miss.

Filtering inside each arm means a hidden category can never rank or leak. Fusing in TypeScript keeps the SQL simple and the ranking testable without a database.

---

### ADR-042: pg-boss worker as a separate process (D72, D73)

**Decision**: A worker process computes the embeddings. It runs from the same image with the `worker` entrypoint and uses pg-boss queues in the app database. Writes enqueue after commit, and a one-minute sweep re-queues anything stale. Both provider keys are optional:
- Without an embedding key (`OPENROUTER_API_KEY`/`OPENAI_API_KEY`), search is text-only.
- Without an Ask key (`OPENROUTER_API_KEY`/`ANTHROPIC_API_KEY`), Ask is off.

**Rationale**: Provider latency and outages must not affect card writes. pg-boss needs no new infrastructure (no Redis), and its singleton keys deduplicate bursts of edits. Because the sweep catches whatever enqueueing misses, a failed enqueue or a model change fixes itself. Optional keys keep local development, CI and forks working without provider accounts.

---

### ADR-043: Committed embedding cache for the search eval (D81)

**Decision**: The search eval reads vectors from `packages/db/test/fixtures/search-embeddings.json`, keyed by `sha256(model + text)`. Only `pnpm test:search:update` (with `OPENROUTER_API_KEY` or `OPENAI_API_KEY`) calls the API and rewrites the file. If the cache lacks any vector the eval needs, the hybrid assertion is skipped and only the text arm is gated.

**Rationale**: CI stays deterministic, free and keyless, while the eval still measures the real model. A change to a fixture, a query or the model shows up as missing cache entries, so results can't drift silently.

---

### ADR-044: OpenRouter as the preferred provider gateway

**Decision**: `ai/providers.ts` builds the embedder and the asker from env. `OPENROUTER_API_KEY` wins and serves both features through OpenRouter's OpenAI-compatible API (`https://openrouter.ai/api/v1`). `OPENAI_API_KEY` (embeddings) and `ANTHROPIC_API_KEY` (Ask) remain as direct fallbacks.
- Embeddings use the OpenAI SDK with a `baseURL`. The stored model stays the bare `EMBEDDING_MODEL` (`text-embedding-3-small`) and the wire model is `openai/<id>`. The vectors are identical, so switching provider re-embeds nothing and the eval cache keys stay valid.
- Ask over OpenRouter uses chat completions with a forced `answer` function call (`ai/openai-chat-asker.ts`). It shares the prompt, schema and citation checks with the Anthropic asker. `ASK_MODEL` is provider-specific; unset, it is `anthropic/claude-haiku-5.5` on OpenRouter or `claude-haiku-5-5` on Anthropic.
- Compose passes `ASK_MODEL` (api) and `EMBEDDING_MODEL` (api + worker) through, so models switch per environment without a code change. `llm_calls` prices by the id sent to the provider (`LLM_PRICES_PER_MTOK`); an unlisted model is logged at cost 0.

**Rationale**: One key and one bill cover both features, and the models can be changed without new provider accounts. The direct keys keep existing setups working.

### ADR-045: Share target in a hand-written service worker (D98)

**Decision**: `vite-plugin-pwa` switches from `generateSW` to `injectManifest` with `src/sw.ts`. The generated worker's rules are ported 1:1 (precache, navigation fallback and denylist, Cloudinary CacheFirst, `SKIP_WAITING`), and a `fetch` handler takes the manifest `share_target` POST to `/share`, stores it in IndexedDB and redirects to the confirm screen. The SW and the share chunk import `@pb/shared/ingest-constants` (zod-free).

**Rationale**: `generateSW` can't answer a POST. A server-side `action: /api/...` would skip the deck picker and the sign-in hand-off. One SW file keeps offline behaviour in one place.

---

### ADR-046: Ingest tokens separate from sessions (D99)

**Decision**: `ingest_tokens` hold sha256 hashes of `ing_` + 32 random bytes, shown once, at most 5 live per user, optionally bound to a deck. They are accepted only by `POST /ingest` (and as the email-in local part); every other route treats them as invalid credentials. Shares made with a token are always `channel = shortcut`. Every non-session token prefix is registered in `lib/token-prefixes.ts`; `session-auth` refuses such bearers off their routes without a database lookup.

**Rationale**: A token lives in a Shortcut or an email address book, so it leaks more easily than a session. Least privilege limits a leak to adding proposals that a publisher still has to approve. `deck_id` lets Phase 12's deck-scoped hosts mint deck-bound tokens.

---

### ADR-047: Entities as a column in the search text (D97)

**Decision**: `items.entities jsonb` holds cross-type facts (phones, addresses, hours, prices, dates, people, urls), validated by `entitiesSchema` and capped at 2 KB. `item_search_text()` takes them as a fifth argument; the generated column and its GIN index were rebuilt, and every item re-embedded through the sweep.

**Rationale**: `payload` is strict and per type; entities apply to any card and are what people search for ("plumber phone"). A separate column keeps payload validation unchanged.

---

### ADR-048: SSRF-guarded fetching at connect time (D102)

**Decision**: The worker fetches shared URLs through an undici `Agent` whose `connect.lookup` resolves the host and rejects private, loopback, link-local, CGNAT, multicast and metadata addresses (`ipaddr.js`, IPv4-mapped IPv6 included). Only http(s) on 80/443, ≤ 3 redirects (each re-checked), 10 s, 3 MB, HTML only.

**Rationale**: This is the first outbound fetch, from a process on the same network as Postgres and the API. Checking at connect time, not before the request, closes DNS rebinding; checking each redirect closes open-redirect hops.

### ADR-049: Spec-driven development with spec-kit, specs committed

**Decisions**:
- **spec-kit 1.2.2** (Claude integration, `sh` scripts) drives planning and implementation from Phase 6 on: `/speckit-specify` → `clarify` → `plan` → `tasks` → `analyze` → `implement` → `converge`. Pinned in `.specify/init-options.json`; run with `uvx --from specify-cli==<version> specify …`, upgrades are deliberate PRs.
- **Constitution** (`.specify/memory/constitution.md`): the existing ground rules and ADRs as seven principles, so every plan's Constitution Check gates on rules that are already true. Versioned (semver); amendments are PRs.
- **Project templates in `.specify/templates/overrides/`** (plan, tasks): the real monorepo layout, a decisions table continuing the `D` series, invariant → test traceability, rollout, risks and a close-out phase (docs, `PLAN.md`, converge). Core templates stay untouched so `specify` upgrades apply cleanly.
- **Specs are committed and public** under `specs/NNN-name/`, numbered sequentially from `006`; `specs/005-phases-0-5` records that Phases 0–5 predate spec-kit. A feature folder is a working contract until its PR merges, then a historical record; durable truth stays in this document, `README.md` and the constitution.
- **`PLAN.md` stays the roadmap**; a phase can span several features. Decisions continue the `D` series (Phase 6 reserves D129–D147); durable ones become the next ADR. Deviations are logged in the feature's `implementation-notes.md` and summarised here at close-out, as before.
- **No spec-kit git extension**: branches and worktrees stay as they are; the active feature is the local `.specify/feature.json`.

**Rationale**: The private phase plans worked, but reviewers could not see them and nothing checked the code against them. Committed specs travel with the PR, and `analyze` and `converge` check them against the code. Building the constitution only from existing rules keeps the gates meaningful rather than aspirational.

### ADR-050: Lifecycle rules in services, called with an actor (D130)

**Decision**: Archive, restore, delete and undelete live only in `items.service`. Each method takes `actor: { user, via }` as its first argument; HTTP routes build it with `getActor(c)` (`via: 'session'`, whether the session came from the cookie or a bearer). Routes only parse and map; transition rules, permissions and problem types are decided once, in the service.

**Rationale**: Phase 8 records history in `item_events` from these same methods, storing `actor.user` and `actor.via`. Phase 13's MCP server calls them with `via: 'mcp'` plus the connection id. Every client gets the same rules and the same audit trail, without duplicating checks per transport.

### ADR-051: Signed direct uploads from the browser (D133)

**Decision**: The editor uploads photos straight from the browser to Cloudinary with a short-lived signature from `POST /decks/{id}/media/sign`. The API signs only for members who may create cards in that deck, and the signature fixes the folder (`gobbit/items/<deckId>`), the tags (`editor`, `deck:<deckId>`) and the allowed formats. The card stores `{ publicId, alt }`. No unsigned preset and no proxying through the API.

**Rationale**: Photos from a phone are several MB; proxying them would tie up the API and its memory for no benefit, and an unsigned preset would let anyone with the cloud name upload. Signing keeps the secret on the server and scopes every upload to a deck, so Phase 7's `assets` table and orphan sweep can find uploads by tag without a schema change now. The size cap is checked in the browser, with Cloudinary's account limit as the backstop; a signed preset can add a server-side cap later without changing the client.

### ADR-052: Browse: native scroll-snap + use-gesture (D139, D140, D144)

**Decision**: Browse pages cards with native CSS scroll-snap and one IntersectionObserver. `@use-gesture/react` (`useDrag`) is used only for horizontal swipes on the header and footer bands, with `touch-action: pan-y` and a 24 px edge guard. Only the current card ±1 is mounted. The gesture library lives only in the lazy Browse route chunk, and `pnpm budget` enforces that.

**Rationale**:
- Native snapping keeps vertical paging on the compositor, with platform physics and no JS per frame, and it works with keyboard and assistive tech.
- A small drag library for the two bands covers what CSS can't do (tap filtering, axis locking) without a carousel framework.
- The edge guard leaves the OS back gestures alone.
- Mounting ±1 bounds the DOM and image decoding regardless of category size.
- The cost is about 8.5 KB gzip, and only for readers who open Browse.

## Summary

Gobbit is a layered REST API with OpenAPI documentation, magic-link sessions, per-deck roles and category visibility, and comprehensive error handling. Data lives in PostgreSQL with invariants enforced at multiple levels (Zod schemas, database triggers, service checks). Pagination uses keyset cursors for stability. The seed creates only the owner user; tests build their data with factories. Testing spans unit (mocked), integration (Testcontainers), and e2e (Playwright smoke). Migrations are versioned with rollback support. Architecture emphasizes single source of truth (@pb/shared), type safety (strict TypeScript), and explicit error codes (RFC 9457). Phase 3 adds the Reader PWA: a static React app in its own Caddy image that also routes `/api` and `/s` to the API on one origin, a generated typed client, offline reading through a persisted query cache, and share previews with lazily rendered Open Graph images. Phase 3B gives every account a personal deck at `/d/me`, created on sign-in, and a minimal text and link card editor. Phase 4 adds hybrid search: trigram and pgvector arms fused with RRF, limited to what the reader can see. It also adds an optional Ask answer with citations, an embeddings worker on pg-boss, and a recall eval backed by a committed embedding cache. Phase 5 adds ingestion: shares from Android, an iPhone Shortcut, a paste box or (optionally) email become jobs that the worker fetches safely, extracts into a proposed card with an LLM, and checks for duplicates; publishers approve them in a review queue. Phase 6 adds the card lifecycle: archive and restore, delete with a 30-day undelete and a weekly purge, all through service methods called with an actor, with optimistic Undo in the web app. It also adds the card editor for every type, with a live preview through the list renderer, zod-free client checks, local drafts and inline category creation. Image cards upload photos straight from the browser to Cloudinary with a signature from the API, and link cards can fetch a preview through the safe fetcher. Browse mode shows one card per screen: readers swipe through a category, across the header to change category and across the footer to change pane, and every gesture also has a button and a key.
